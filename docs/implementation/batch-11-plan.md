# Batch 11 实施计划

## 交付范围

Batch 11 建立统一通知平台：消费版本化领域事件，以 Inbox 去重生成 Notification Intent，
再根据当前收件人、偏好、同意、安静时段和抑制状态创建站内通知或邮件 Delivery。模板发布、
发送尝试、提醒、摘要、Provider 回执和运营群发都保留不可变版本或审计链。

## 实施顺序

1. 新增事件、Intent、模板、Delivery、偏好、提醒、群发、Webhook 和抑制迁移。
2. 建立严格事件版本、收件人解析、去重、模板 Schema/安全渲染与受控 Route Registry。
3. 实现站内通知、未读计数、偏好、同意和分类退订 API。
4. 实现 Provider 接口、Mailpit/Fake、稳定幂等、错误分类、退避与 Dead Letter。
5. 实现提醒重算/派发、摘要窗口、不可变群发受众、审批分离、暂停和取消。
6. 实现 Provider Webhook 验签/去重、退信/投诉抑制和有理由解除。
7. 实现用户通知中心、偏好/退订页面和管理端通知运营中心。
8. 运行单元、集成、并发、Provider、安全、双端 E2E 和 Batch 1-10 回归。

## 强制不变量

- 上游业务事务不直接调用邮件 Provider，通知失败不回滚已成功业务。
- 未知事件版本保留原事件并进入 Dead Letter，不猜测 Payload。
- 同一来源事件、Intent/用户、Intent/渠道、Webhook 和 Campaign/用户均数据库唯一。
- 营销默认拒绝，只有显式同意才发送；安全、支付和必要服务通知不能被营销退订关闭。
- 模板激活后不可原地修改，渲染只允许 Schema 变量，拒绝脚本、危险协议和开放重定向。
- 发送时重新验证账户、验证邮箱、偏好、同意、抑制、过期和业务状态。
- Provider 元数据不包含辅导内容、AI 对话、风险记录、密码 Token 或私人档案。
- 群发审批者与创建者分离，敏感辅导/AI/婚恋资料不能作为普通运营受众条件。

## 验收边界

本地使用 PostgreSQL、Redis、Mailpit/Fake Provider 和浏览器验收。生产邮件供应商、法域退订
规则、营销同意文本、正式保留期、点击跟踪、群发审批阈值和供应商 SLA 在批准前保持
`undecided` / `NOT_RUN`，生产配置拒绝 Mailpit/Fake。

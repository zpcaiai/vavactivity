# 管理端左侧导航 · 功能闭环差距矩阵

审计时间：2026-08-11
审计对象：`vavactivity` 主仓 `apps/admin-web`（当前工作副本）× `services/api`（913 个后端端点）
审计方法：逐项比对 `router/index.ts` 的 `*SectionPermissions` 声明 → 页面组件实际发起的请求 → 后端 `admin_router.py` 的写端点清单

---

## 0. 一句话结论

后端不是瓶颈。**913 个后端端点里，能在管理端 UI 触发的写操作不到 25%**；左侧 29 个导航项中，**12 项是纯只读看板**（只有列表，没有创建/编辑/状态流转），另有 **6 处「假 section」**（前端声明了 tab，后端没有对应资源，或前端借用了别的 section 的数据做占位渲染，字段根本对不上）。

昨晚已闭环的 4 项（用户管理、辅导中心、网站设置、管理员）不在下表缺口内。

## 1. 全局分级总览

| 等级 | 含义 | 数量 |
|---|---|---|
| 🔴 P0 | 核心流程断裂，运营在后台根本做不完一件事，只能绕开后台直接调 API / 写库 | 28 项 |
| 🟠 P1 | 有变通路径但别扭，或影响审计合规 | 31 项 |
| 🟡 P2 | 打磨类 | 18 项 |

### 五个跨模块的结构性问题（不是零散疏漏）

1. **只有「批准」没有「创建」**——后端 90+ 个写端点中能在 UI 触发的不到 20 个，且几乎全是 approve/activate 这类二元动作。质量需求、设计 token、通知模板、会员计划版本、安全规则、推荐策略、推荐实验……**都只能审批已存在的记录，但没有任何界面能把这条记录创建出来**。
2. **认证/发布收尾环节全线缺失**——quality / experience / process / data-governance / admin-platform 五个模块的 `certifications/evaluate` + `/{id}/decide` **无一在前端可触发**。也就是「治理走完 → 能上线」这条链路，目前只能绕开后台。
3. **审计理由字段被前端硬编码**——`decideBaseline`、`reviewAudit`、`disableInstallation`、`changeMaintenance`、`decideModeration` 等动作的 `reason` / `reason_code` 是写死的固定英文文案。每条审计记录理由都一样，这些模块自我标榜的"不可变审计轨迹"实际形同虚设。**且存在合规倒挂**：隐私模块的 `erasure execute`（真删数据）和 `break-glass use`（紧急访问）这两个最高风险动作反而不传 reason，而风险更低的 approve 反而传了。
4. **借用数据占位**——技能控制台的 dependencies / permissions / incidents / audit / publishers 五个 tab、关系运营中心的 8 个 tab、会员的 sku-mappings 与 plan-versions，点进去看到的是**别的接口的数据**，字段对不上。运营看到的是假页面。
5. **列表只有 3 列 + 无详情页**——治理类 6 个模块共用的壳组件只渲染「标识/类型/状态」，payload 里的责任人、截止日期、影响范围、evidence_manifest 全看不到，更点不进子资源（如流程实例的步骤列表）。

## 2. 逐模块缺口

## 3. 建议的推进批次

按「运营现在就卡住」→「合规风险」→「治理收尾」排序：

| 批次 | 内容 | 理由 |
|---|---|---|
| **B1** | 合作联系记录写操作、交易发起退款、知识库授权治理、课程 SKU 映射、商品分类、文章/见证正文编辑 | 全是「客户已经在等」的业务链路，且后端就绪，纯前端接线 |
| **B2** | 流程治理 interventions 解决 + 实例详情、数据治理 erasures/backfills、隐私 holds/exports/身份核验、AI 转介 assign/resolve | 卡死流程与合规风险，后端就绪 |
| **B3** | 会员 plan-versions + 人工赠送 + 配额调整、推荐策略/实验创建、通知模板发布全流程 + 修 5 处 tab 路由 bug | 「只能批不能建」的源头断裂 |
| **B4** | 信任安全状态机对齐 + restrictions、系统运维 releases/jobs、技能控制台数据源纠偏 + 供应链门禁 | 需要先对齐后端状态机语义，改动较深 |
| **B5** | 质量/设计/体验/数据治理的创建表单与 certifications 收尾、usability 子模块从零建、统一管理平台定去留 | 治理类，量最大，且部分需产品决策 |
| **B6** | 全局：把硬编码 reason 换成必填输入框；通用「详情抽屉 + 表单弹窗」组件抽取；工作台接真实指标 | 横切改造，建议在 B1–B3 过程中顺手抽组件 |

### 需要后端先动的两处

1. **关系运营中心**：stages / proposals / pauses / endings / milestones / reminders / checkins / audit 的查询端点与死信处置端点不存在，接近半个新模块。在后端补齐前，前端应先把这 8 个假 tab 摘掉，而不是继续用 journeys 数据冒充。
2. **会员 incidents**：`ADMIN_RESOURCE_PERMISSIONS` 无此 key，请求 404。若无事件表，前端应移除该 tab。
3. 次要：`content` 模块需为 articles/testimonials 补 localization PUT 与 approve/reject（目前只有 pages 有）；`notifications` 若保留 unsubscribes 需补一个 GET 列表端点。

## 4. 工作量量级

| 分组 | 前端 | 后端 |
|---|---|---|
| 内容与交易 | 3–4 人周 | 1–2 人天 |
| 运营类 | 2–3 人周 | 少量 |
| 婚恋类 | 6–10 人天 | 关系模块约半个新模块 |
| 治理类 | 9–12 人周（含 usability 从零建） | 少量 |

治理类占了总量的一半以上，且其中很大比例是「同一个模式重复 N 次」——**先抽一套通用的「列表 + 详情抽屉 + 创建/编辑弹窗 + 状态流转按钮组 + 必填理由」组件，后面几个模块的工作量会显著下降**，这是最值得先做的一件事。

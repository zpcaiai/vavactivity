# Goal

Implement Batch 13 in the order recorded in `docs/implementation/batch-13-plan.md`.

Build one dating profile per eligible member on top of versioned schemas and taxonomies,
with protected-date-of-birth adult eligibility, faith / relationship-history / family /
lifestyle detail, multilingual narratives, private reviewed photos, hard and soft partner
criteria, field-level privacy, backend-authoritative completeness, immutable versions,
a field- and photo-level review workflow, and de-identified recommendation projections
for Batch 14.

# Prerequisites

1. Read `project-manifest.yaml`.
2. Verify Batch 1 through Batch 12; `make privacy-verify` must still pass.
3. Read every skill under `skills/batch-13`.
4. Inspect the Identity, Privacy, Media, Activity, Notification, RBAC and Audit contracts.
5. Record unresolved gender, relationship-eligibility, faith-taxonomy, profile-visibility and
   contact-exchange policies in `docs/product/decision-register.md`.

# Architecture constraints

- General user profiles (Batch 12) and dating profiles remain separate domains.
- Payment, counseling and AI data are never copied into a dating profile.
- A member may hold exactly one dating profile.
- Schemas and taxonomies are versioned; an active release is immutable.
- Submitted and approved profile versions are immutable, enforced in the database.
- Draft edits never overwrite the approved version other members are seeing.
- Viewer-specific DTOs are generated by the backend; frontend hiding is not privacy.
- Recommendation projections carry only approved, necessary, normalised fields.
- Matching, ranking and like behaviour belong to Batch 14 and Batch 15.
- AI availability must never block profile editing or review.

# Eligibility invariants

- Dating profiles require the configured adult age (`DATING_MINIMUM_AGE`, at least 18).
- Age is computed by the backend from the Batch 12 protected date of birth.
- A client-submitted age value is never authoritative.
- Suspended, deletion-pending and ineligible accounts cannot enter the recommendation pool.
- An eligibility change invalidates the projection.

# Privacy invariants

- New profiles start in strict mode; every field is registered with the privacy control plane.
- Visibility is evaluated at query time, per view context.
- Contact details are never exposed automatically — mutual match included.
- AI profile access requires the Batch 12 consent.
- Blocked and restricted members cannot reach each other's profiles.
- Sensitive administrative access needs a separate permission and is audited.
- Privacy changes invalidate caches and rebuild projections immediately.

# Completeness invariants

- Completeness is computed by the backend from the active schema policy.
- A missing mandatory field blocks submission regardless of the aggregate score.
- Recommendation eligibility may demand a higher threshold than submission.
- Completeness measures form completion, never personal quality or suitability.
- Snapshots preserve the policy version.

# Photo invariants

- Originals stay private; storage keys never appear in a DTO.
- File type, size and image decoding are verified; a spoofed MIME type is rejected.
- EXIF and other metadata are removed by re-encoding from raw pixels.
- Unapproved and rejected photos are invisible to other members.
- Exactly one approved primary photo may be live.
- Access uses short-lived viewer-bound tokens, revoked on deletion or rejection.
- Biometric identification and cross-site face search stay disabled.
- Automated moderation is advisory unless an approved policy says otherwise.

# Preference invariants

- Preferences are private to the owner and the recommendation engine.
- Hard constraints are explicit and marked `required`.
- Hard criteria are never relaxed without the member's acknowledgement.
- Only approved criteria may enter automated filtering.
- Nothing is inferred from narrative text.
- Contradictory criteria are explained to the member.

# Review invariants

- Submission creates an immutable version and a review case.
- Editing during review creates a separate draft version.
- The existing approved version keeps serving other members until a replacement is approved.
- Decisions may apply to individual fields or photos; a blocking item prevents approval.
- Rejection and suspension require reasons.
- Reviewers cannot rewrite member statements.
- Automated checks may assist but never silently assert identity fraud.
- Concurrent decisions are rejected by optimistic locking, never silently merged.
- Every review and sensitive read is audited without storing narrative or photo content.

# Failure policy

When a field or taxonomy policy is unresolved: record it in the decision register, keep the
field optional, use a restricted privacy default, invent no permanent social or theological
policy, and continue with unrelated capabilities.

When a privacy test fails: stop the release, invalidate caches and projections, identify the
missing viewer/purpose/relationship check, fix backend DTO generation, add a regression test
and rerun the profile and privacy security suites.

When a photo-security test fails: remove the photo from all projections, revoke its view
tokens, repair processing or access control, add a regression test and rerun the media and
photo suites.

When review concurrency fails: preserve both competing decisions, prevent either from silently
overwriting the other, repair optimistic locking, add a regression test and rerun the review and
projection suites.
